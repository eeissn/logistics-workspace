# Выпуск кандидата схемы 3 и откат без потери новых записей

Это план, не разрешение на production. Последний проверенный рабочий сервер: `3f2ef13398acb6b4a76f37c24ba0a17b2635414b`. Кандидат находится в PR #49 / codex/workspace-followup-20261119. Перед действиями подтвердить полный SHA и зелёный CI именно этого SHA.

## Что меняется

SQLite получает только таблицу saved_views с владельцем, ревизией и JSON правил. Пользователи, соли/пароли, сессии, заявки, их позиции и ревизии не мигрируются и не удаляются. Google Sheets выключен, пока отдельно не предоставлены credentials/режим работы. PDF по решению владельца не хранятся. Windows Audit уже установлен отдельно и не является частью этого выпуска.

## Разрешённая локальная репетиция

`python -m unittest backend.test_schema_compatibility -v` проверяет цикл3→2→3 на временных синтетических SQLite, сохранность всех строк/ревизий и backup/restore.

`python -m backend.rehearse_previous_release` дополнительно загружает **закреплённый исторический backend из Git**, не конфигурацию VPS: оба синтетических аккаунта проходят новуюAPI3 → предыдущуюAPI2 → новуюAPI3. Проверяются существующие сессии, изоляция, сохранение новых заявок при откате и сохранённые виды после повторного обновления. Для команды нужна полная история Git. DATABASE_PATH и реальные документы не используются.

`python -m deploy.schema_compatibility "/path/to/isolated.sqlite3"` по умолчанию только проверяет целостность, схему и счётчики. Режим `--set-schema2-marker` изменяет **только PRAGMA user_version** после проверки известной схемы saved_views. Таблица и все её данные сохраняются. Использовать на production можно только по отдельному разрешению и при остановленных писателях.

## Конкретный план production после согласования

1. Сверить SHA, чистоту checkout, пути службы/venv/SQLite, свободное место, доступ по закреплённому ключу и рабочую зашифрованную копию. Не выводить env/ключи/содержимое заявок в отчёт.
2. Назначить короткое окно без редактирования обоими пользователями. Сохранить текущую сборку и полный SHA отката. Остановить API, создать отдельный SQLite online-backup и проверить integrity/foreign keys. Сохранить исходный файл; существующие рабочие копии не удалять.
3. Установить согласованный кандидат и собрать обычный интерфейс (не демо). Google не включать. Запустить службу: транзакционная миграция2→3 создаёт новую таблицу и проверяет её структуру. Отдельные таблицы заявок не переписываются.
4. Проверить обе службы, HTTPS200, API401 без сессии, MIME PDF-worker. Владелец проверяет вход/реестр/известную заявку, ЭТРН, историю и сохранённый вид на двух устройствах; опасных массовых операций не выполнять ради теста.
5. Проверить следующую штатную зашифрованную копию и получение на домашний Windows. Не путать установку кода с приёмкой восстановления/физического Safari.

## Проверенный механизм отката

Простой checkout старого backend при user_version3 не работает. Возврат старой предрелизной базы после пользовательских изменений также недопустим: он потеряет новые заявки.

1. Остановить API и подтвердить отсутствие других писателей. Сохранить и проверить **актуальную** копию схемы3 со всеми изменениями после выпуска, а не использовать старый снимок вместо неё.
2. Пока установлен код кандидата, выполнить согласованный `deploy.schema_compatibility --set-schema2-marker` на проверенном пути SQLite от имени пользователя службы. Меняется лишь маркер версии3→2, saved_views и бизнес-данные остаются на месте. Не выполнять при неизвестной версии/структуре; проверки должны отказать, а не угадывать.
3. Выбрать прежний полный SHA и прежнюю сборку, запустить API2. Предыдущий сервер игнорирует дополнительную таблицу и продолжает работать с текущими заявками/ревизиями. Виды остаются в базе, но старый интерфейс их не синхронизирует.
4. Проверить те же HTTP/службы/вход/изоляцию. Если любой шаг не подтверждён, не восстанавливать старую базу автоматически и не удалять таблицы; сохранить актуальный снимок для отдельного расследования.
5. При повторном переходе к исправленному кандидату initialize2→3 проверяет и повторно использует сохранённую таблицу. Виды и записи, добавленные при работеAPI2, остаются доступны.

Нельзя применять этот протокол к будущей схеме4 или иному историческому серверу: репетиция закреплена на указанном API2. Путь SQLite, момент остановки, команды sudo и SHA должны быть сверены перед отдельным одобрением владельца. Ни один из production-шагов этой сессией не выполнен.
