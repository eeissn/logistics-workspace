# Обслуживание Logistics Workspace

Рабочая ветка — `feature/two-user-sync`. Приложение работает на Ubuntu 24.04, вход администратора — `admin`, каталог проекта — `/opt/logistics-workspace/logistics-workspace`. Публичный адрес — `https://logistics-sputnik.duckdns.org`. Имена службы и пути к данным, резервным копиям и venv описаны в [руководстве сервера](../backend/README.md). Перед первым обновлением сверьте эти пути с VPS. История проекта фиксирует работу двух аккаунтов, HTTPS, ежедневных копий и обновления TLS. Состояние служб и установленный коммит требуют проверки с домашнего ПК.

## SSH и диагностика

Сверьте ED25519-отпечаток по веб-консоли провайдера или с компьютером, который уже доверяет серверу. После регистрации проверенного ключа сервера выполните с домашнего ПК:

```powershell
ssh -o BatchMode=yes -o PreferredAuthentications=publickey -o StrictHostKeyChecking=yes admin@170.168.18.148 'whoami; hostname'
```

При отсутствии клиентского ключа подготовьте отдельный ключ Ed25519 и зарегистрируйте его открытый ключ через доверенный вход после согласования. Храните закрытый ключ в профиле Windows с ограниченным доступом. Проверьте вход по ключу отдельным подключением при действующем способе восстановления доступа.

После входа выполните диагностику без повышения прав:

```bash
git -C /opt/logistics-workspace/logistics-workspace status -sb
git -C /opt/logistics-workspace/logistics-workspace rev-parse HEAD
systemctl is-active logistics-workspace nginx
systemctl list-timers --all certbot.timer
ss -ltn
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:8000/api/records
```

Для повседневных проверок выделите отдельный SSH-ключ и учётную запись с доступом только к диагностике. Для неё достаточно разрешить проверку версий, статусов и HTTP без чтения файла окружения, базы и копий. Установка ключа и назначение прав согласуются отдельно. Используйте административный вход для согласованного выпуска.

## Подготовка выпуска

1. На рабочей ветке запустите серверные тесты, тесты интерфейса и сборку. Проверьте, что сборка использует серверный режим. Зафиксируйте полный SHA кандидата и перечень изменений. В GitHub запускаются те же проверки. Публикация коммита запускает проверки без доступа к VPS.
2. Через SSH соберите текущий SHA, состояние рабочей копии, версию SQLite-схемы и состояние служб. Сверьте расписание копий и сертификата с действующей конфигурацией. При локальных правках или расхождении путей остановите подготовку до выяснения причины.
3. Подготовьте сборку точного SHA отдельно от рабочего каталога. При изменении зависимостей подготовьте отдельный venv. При изменении схемы проверьте обновление на защищённой копии базы на VPS. Сохраните перечень файлов и действий для возврата к текущей версии.
4. Получите отдельное согласие владельца на развёртывание указанного SHA.

## Обновление и откат

1. Для согласованного выпуска сохраните текущий SHA, сборку и версию окружения. При остановленном API сделайте новую уникальную резервную копию SQLite штатной командой и проверьте её через `PRAGMA integrity_check;`. Подробности — в [разделе о резервном копировании](../backend/README.md#резервные-копии). При ошибке копирования или проверки возобновите работу текущей версии.
2. Установите подготовленный код и сборку согласованного SHA и запустите службу. Проверьте статусы systemd и активный SHA. Запустите `bash deploy/check-release.sh` для проверки TLS, HTTP 200 главной страницы и HTTP 401 на `/api/records` без сессии. Проверку с рабочими аккаунтами проводите только в согласованных пределах.
3. При сбое остановите API и верните предыдущий код, сборку и окружение. Если схема совместима, используйте текущую базу. Если требуется восстановление, сначала сохраните отдельную копию текущей базы и определите, были ли записи после выпуска. Согласуйте восстановление с владельцем, затем следуйте инструкции по восстановлению SQLite. После запуска повторите проверки HTTP, TLS и службы.
