# Обслуживание Logistics Workspace

Рабочая ветка — `feature/two-user-sync`. Приложение работает на Ubuntu 24.04, вход администратора — `admin`, каталог проекта — `/opt/logistics-workspace/logistics-workspace`. Публичный адрес — `https://logistics-sputnik.duckdns.org`. Имена службы и пути к данным, резервным копиям и venv описаны в [руководстве сервера](../backend/README.md). Перед первым обновлением сверьте эти пути с VPS. История проекта фиксирует работу двух аккаунтов, HTTPS, ежедневных копий и обновления TLS. Состояние служб и установленный коммит требуют проверки с домашнего ПК.

## SSH и диагностика

Сверьте ED25519-отпечаток по веб-консоли провайдера или с компьютером, который уже доверяет серверу. После регистрации проверенного ключа сервера выполните с домашнего ПК:

```powershell
ssh -o BatchMode=yes -o PreferredAuthentications=publickey -o StrictHostKeyChecking=yes admin@170.168.18.148 'whoami; hostname'
```

При отсутствии клиентского ключа подготовьте отдельный ключ Ed25519 и зарегистрируйте его открытый ключ через доверенный вход после согласования. Храните закрытый ключ в профиле Windows с ограниченным доступом. Проверьте вход по ключу отдельным подключением при действующем способе восстановления доступа.

После входа выполните диагностику без повышения прав:

```bash
git -C /opt/logistics-workspace/logistics-workspace status -sb
git -C /opt/logistics-workspace/logistics-workspace rev-parse HEAD
systemctl is-active logistics-workspace nginx
systemctl list-timers --all certbot.timer
ss -ltn
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:8000/api/records
```

Для повседневных проверок выделите отдельный SSH-ключ и учётную запись с доступом только к диагностике. Для неё достаточно разрешить проверку версий, статусов и HTTP без чтения файла окружения, базы и копий. Установка ключа и назначение прав согласуются отдельно. Используйте административный вход для согласованного выпуска.

## Зашифрованная доставка на Windows

Локальный прогон из корня проекта: `python -m unittest deploy.test_backup_delivery -v`. Тест создаёт временную SQLite, временные ключи, публикует и получает CMS из имитированного SFTP-каталога, проверяет SHA-256, свежесть, ротацию, расшифровку AES-256-GCM и чтение восстановленных данных. Сценарий API с двумя аккаунтами на восстановленной тестовой SQLite входит в `backend.test_app`.

### План включения на VPS после отдельного согласования

1. С доверенного административного входа проверить действующий ночной скрипт, часовой пояс cron, реальный путь сертификата, UID/GID и домашний каталог `logistics-backup`. Сохранить копии изменяемых конфигураций SSH и заданий. Текущую цепочку создания и ротации SQLite оставить действующей.
2. Подготовить отдельный chroot, например `/srv/logistics-backup`. Сам chroot и все родители принадлежат root и недоступны для записи группе и остальным. Создать внутри `outbox` с владельцем `logistics` и правами `0755`. Внутри chroot доступны только CMS и метаданные. Ограничить чтение самого chroot служебной группой, участники которой сверены заранее. Каталог с исходными SQLite остаётся вне chroot.
3. Дополнительный шаг ночного задания от `logistics` вызывает `python deploy/backup_delivery.py publish <готовая-SQLite> <публичный-сертификат> <outbox> <UTC-время-создания>` сразу после успешного создания штатной копии. Передавайте UTC времени **исходного снимка** в виде `20261114T000002Z`. Команда ожидает файл без sidecar, проверяет SQLite и публикует одну пару CMS и JSON (размер и SHA-256) атомарным переименованием каталога. Протоколу не требуются права на рабочую БД. После отдельного теста ротации на сервере удалять по возрасту только комплекты, созданные этим публикатором, например старше 30 дней. Штатная ротация SQLite остаётся самостоятельной.
4. Подготовить отдельный ключ загрузки Ed25519 без парольной фразы. Только Windows-пользователь задачи должен иметь доступ к приватному ключу. Публичный ключ зарегистрировать с префиксом `restrict` в отдельном root-managed `AuthorizedKeysFile`. Ключ нельзя использовать для других аккаунтов. Действующий интерактивный ключ не требуется для задания.

Предлагаемый блок SSH после проверки фактических путей и положения `Match` в конфигурации:

```sshconfig
Match User logistics-backup
    AuthorizedKeysFile /etc/ssh/authorized_keys/%u
    ChrootDirectory /srv/logistics-backup
    ForceCommand internal-sftp -R -d /outbox
    AuthenticationMethods publickey
    PasswordAuthentication no
    DisableForwarding yes
    PermitTTY no
```

Перед перечитыванием проверить `sshd -t` и итоговый `sshd -T -C user=logistics-backup,host=localhost,addr=<IP-клиента>`. Сохранить открытую административную сессию. После reload проверить независимый административный вход. С выделенным ключом проверить скачивание CMS, отказ записи/удаления, отсутствие доступа к SQLite, отказ shell и forwarding. При ошибке отключить упаковывающий шаг, восстановить предыдущую SSH-конфигурацию и список ключей, проверить `sshd -t` и перечитать SSH из сохранённого административного входа. Сохранить существующие архивы.

### Windows

Используйте Python 3.12+, NTFS, встроенный OpenSSH и отдельный каталог архива с доступом только у владельца Windows и системных администраторов. Заранее заполните отдельный `known_hosts` с ключом VPS, отпечаток которого сверили доверенным способом. Приватный ключ расшифрования CMS храните отдельно, с парольной фразой. Заданию нужен только специальный SSH-ключ чтения.

В PowerShell из каталога той версии проекта, которую будет запускать Планировщик, заполните параметры своими путями:

```powershell
$backup = @{
    Python = 'C:\Path\python.exe'
    Server = 'backup.example.com'
    Identity = 'C:\Private\logistics-download'
    KnownHosts = 'C:\Private\logistics-known-hosts'
    Destination = 'C:\Private\LogisticsArchives'
}
.\deploy\pull-backup.ps1 @backup
.\deploy\install-backup-task.ps1 @backup
Start-ScheduledTask -TaskName 'Logistics Workspace Backup'
Get-ScheduledTaskInfo -TaskName 'Logistics Workspace Backup'
```

Задание запускается после входа владельца в Windows и в 08:00, 14:00 и 20:00 в его сеансе. После ночи с выключенным ПК архив будет получен при следующем входе. Задача выполняется с обычными правами и без сохранённого пароля Windows. Проверьте первый ручной запуск и повторный вход после перезагрузки. Код возврата и время видны в Планировщике и `backup-delivery.log`. Ошибка вызывает видимое окно в сеансе. Свежесть по умолчанию 36 часов, ротация локальных проверенных архивов через 45 дней. Старые вручную сохранённые архивы хранятся отдельно или остаются вне журнала получателя. SHA-256 сверяет размер и байты в защищённом SFTP-канале. Аутентичность CMS проверяет OpenSSL при расшифровке.

Для учебного восстановления расшифруйте синтетический CMS через `openssl cms -decrypt -binary -inform DER -in <archive.cms> -recip <certificate.pem> -inkey <private-key.pem> -out <isolated.sqlite3>`. Проверьте `PRAGMA integrity_check` и выполните отдельный запуск API на этом временном файле. Для отключения доставки выполните `Disable-ScheduledTask -TaskName 'Logistics Workspace Backup'`.

## Подготовка выпуска

1. На рабочей ветке запустите серверные тесты, тесты интерфейса и сборку. Проверьте, что сборка использует серверный режим. Зафиксируйте полный SHA кандидата и перечень изменений. В GitHub запускаются те же проверки. Публикация коммита запускает проверки без доступа к VPS.
2. Через SSH соберите текущий SHA, состояние рабочей копии, версию SQLite-схемы и состояние служб. Сверьте расписание копий и сертификата с действующей конфигурацией. При локальных правках или расхождении путей остановите подготовку до выяснения причины.
3. Подготовьте сборку точного SHA отдельно от рабочего каталога. При изменении зависимостей подготовьте отдельный venv. При изменении схемы проверьте обновление на защищённой копии базы на VPS. Сохраните перечень файлов и действий для возврата к текущей версии.
4. Получите отдельное согласие владельца на развёртывание указанного SHA.

## Обновление и откат

1. Для согласованного выпуска сохраните текущий SHA, сборку и версию окружения. При остановленном API сделайте новую уникальную резервную копию SQLite штатной командой и проверьте её через `PRAGMA integrity_check;`. Подробности — в [разделе о резервном копировании](../backend/README.md#резервные-копии). При ошибке копирования или проверки возобновите работу текущей версии.
2. Установите подготовленный код и сборку согласованного SHA и запустите службу. Проверьте статусы systemd и активный SHA. Запустите `bash deploy/check-release.sh` для проверки TLS, HTTP 200 главной страницы и HTTP 401 на `/api/records` без сессии. Проверку с рабочими аккаунтами проводите только в согласованных пределах.
3. При сбое остановите API и верните предыдущий код, сборку и окружение. Если схема совместима, используйте текущую базу. Если требуется восстановление, сначала сохраните отдельную копию текущей базы и определите, были ли записи после выпуска. Согласуйте восстановление с владельцем, затем следуйте инструкции по восстановлению SQLite. После запуска повторите проверки HTTP, TLS и службы.
