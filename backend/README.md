# Logistics Workspace с синхронизацией

## Подключение Google Sheets к тестовому стенду

По умолчанию сервер не создаёт маршрут записи. Для отдельного стенда соберите интерфейс с `VITE_SHEET_PREVIEW=true` и запустите API с `WORKSPACE_SHEETS_ENABLED=true` и `WORKSPACE_SHEETS_CONFIG`, указывающим на закрытый JSON. Ключи конфигурации: `spreadsheet` (ID учебной таблицы), `tab` (точное имя вкладки), `headers` (словарь фактических заголовков A1:F1 в порядке слева направо), `actors` (словарь email → имя), `token_file` (путь к файлу короткоживущего OAuth-токена). Источник токена должен обновляться вне приложения. Права выдаются сервисной учётной записи только на согласованную таблицу. Файл конфигурации и токен хранить вне Git с ограниченными правами.

Ключи отображения заголовков: `number`, `title`, `amount`, `actor`, `requested`, `promised`. Текущий адаптер ожидает выделенный диапазон A:F с заголовками в первой строке. Перед записью он сверяет заголовки и отправляет строку в режиме RAW, с ISO-датами как текстом и суммой как числом. Запрос с теми же нормализованными значениями от того же аккаунта повторно не отправляется. При неопределённом исходе SQLite сохраняет блокировку повтора. Оператор сверяет фактическую строку в таблице перед любой ручной разблокировкой. Проверка на настоящем листе, схема его формул и сопоставление столбцов требуют отдельного согласования.

Два вручную созданных аккаунта входят по почте и паролю. У каждого аккаунта свой реестр, ревизия, архив и отчёты по марже. Сервер выбирает реестр по идентификатору пользователя из сессии. Один аккаунт синхронизирует свои заявки между устройствами. PDF читаются в браузере, а на сервер отправляются поля заявок. Реестр сохраняется целиком с номером ревизии. Если реестр успел измениться, сервер возвращает 409. Вкладка запрашивает изменения каждые 15 секунд, при возвращении на неё и после восстановления связи. Открытая форма проверяет, что конкретная заявка сохранила прежнюю версию.

## Локальная проверка

Из корня репозитория в Bash с Python 3.12+ и Node 22.12+ выполните команды. Для Windows можно использовать WSL.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements-test.txt
python -m unittest backend.test_app -v
npm ci
npm test
npm run build

export DATABASE_PATH="$(mktemp -d)/workspace.sqlite3"
export APP_ORIGIN=http://localhost:5173
python -m backend.app add-user first@example.test
python -m backend.app add-user second@example.test
python -m uvicorn backend.app:from_env --factory --host 127.0.0.1 --no-access-log
```

Введите для каждого тестовый пароль из 12–256 символов. Во втором терминале выполните `npm run dev -- --host localhost --port 5173 --strictPort` и откройте [localhost:5173](http://localhost:5173). Для проверки создайте три независимых профиля браузера. В двух войдите под первым аккаунтом, в третьем под вторым. Сохраните вымышленную заявку в первом профиле и нажмите «Обновить» в двух остальных. Заявка должна появиться только во втором профиле первого аккаунта. Проверьте там же архив и отчёт по марже. Во втором аккаунте можно создать заявку с тем же номером и другим содержанием. Затем откройте первую заявку в двух профилях первого аккаунта, сохраните правку в одном и убедитесь, что второй профиль показывает конфликт при сохранении.

Чтобы перенести старый реестр, откройте приложение на прежнем адресе в браузере, в котором хранились заявки. После входа выберите «Перенести заявки с устройства» и подтвердите действие. Совпадающие номера пропускаются, исходная копия остаётся в браузере. Хранилище браузера привязано к схеме, домену и порту сайта, поэтому при их смене кнопка увидит только данные нового адреса. Для переноса между разными origin нужен отдельный экспорт или исходный Excel. В публичном демо `VITE_DEMO=true` используется прежнее локальное хранилище.

## Переход с общего реестра SQLite

1. Перед первым запуском новой версии остановите старый сервис и сделайте резервную копию базы командой из раздела «Резервные копии». Проверьте копию через `PRAGMA integrity_check;`. Для первого прогона используйте отдельную копию SQLite.
2. При запуске сервер переводит схему с версии 1 на версию 2 в одной транзакции. Общие заявки и их ревизия остаются в таблицах `legacy_shared_orders` и `legacy_shared_registry`. API эти таблицы не читает. Аккаунты и хеши паролей сохраняются, прежние сеансы отзываются. После повторного входа личные реестры пусты.
3. Проверьте `PRAGMA user_version;`, число строк в `legacy_shared_orders` и оба входа. Разбирайте принадлежность старых заявок по копии базы с ограниченным доступом. Перенос конкретных заявок возможен после подтверждения владельцев. Перед откатом остановите сервис и сохраните отдельную копию базы версии 2, если в неё уже внесли заявки. Затем восстановите исходную резервную копию версии 1 и запустите предыдущий код.

## Подготовка VPS после проверки ветки

1. Создайте системного пользователя и группу `logistics`. Дайте им доступ на чтение к коду и venv и владение каталогами `/opt/logistics-workspace/data` и `/opt/logistics-workspace/backups` с правами `0700`. Nginx должен иметь доступ на чтение только к сборке и возможность пройти родительские каталоги. Установите зависимости из `backend/requirements.txt` в серверный venv и соберите фронтенд через `npm ci` и `npm run build` с выключенным деморежимом.
2. Создайте `/etc/logistics-workspace.env` с владельцем root и правами `0600`. Укажите фактическое доменное имя в `APP_ORIGIN` без завершающего слеша.
   ```ini
   DATABASE_PATH=/opt/logistics-workspace/data/workspace.sqlite3
   APP_ORIGIN=https://workspace.example.com
   ```
3. Из каталога репозитория создайте два аккаунта командой ниже, подставляя каждую почту. Пароль вводится в терминале без отображения.
   ```bash
   sudo -u logistics env DATABASE_PATH=/opt/logistics-workspace/data/workspace.sqlite3 \
     /opt/logistics-workspace/backend-venv/bin/python -m backend.app add-user first@example.test
   ```
4. Установите юнит из `deploy/logistics-workspace.service` в `/etc/systemd/system/`, выполните `sudo systemctl daemon-reload` и `sudo systemctl enable --now logistics-workspace`. Проверьте, что API слушает только loopback через `ss -ltn`. Запрос `curl -i http://127.0.0.1:8000/api/records` должен вернуть 401.
5. Выпустите сертификат через DNS-01 при закрытых публичных портах 80 и 443. Установите конфигурацию `deploy/nginx.conf`, подставив домен и пути сертификата. Проверьте через `sudo nginx -t` и перезагрузите Nginx. Через SSH-туннель либо локальную проверку с `curl --resolve workspace.example.com:443:127.0.0.1 https://workspace.example.com/api/records` проверьте TLS и 401. Проверьте вход и выход тестового пользователя через HTTPS до открытия 443. Оставьте 80 закрытым, если используете DNS-01 для обновления сертификата. После открытия 443 отдельно проверьте доступ без VPN с устройства коллеги.

## Резервные копии

Запускайте ежедневно с уникальным именем файла. Команда создаёт согласованную копию SQLite и отказывается перезаписывать существующий файл.

```bash
sudo -u logistics env DATABASE_PATH=/opt/logistics-workspace/data/workspace.sqlite3 \
  /opt/logistics-workspace/backend-venv/bin/python -m backend.app backup \
  "/opt/logistics-workspace/backups/workspace-$(date -u +%Y%m%dT%H%M%SZ).sqlite3"
```

Храните зашифрованную копию вне VPS. В базе есть паспортные данные, хеши паролей и данные сессий. Перед восстановлением проверьте копию через `sqlite3 /path/to/backup.sqlite3 'PRAGMA integrity_check;'`. Остановите сервис, перенесите старую базу и её файлы `-wal` и `-shm` в защищённый каталог, затем установите копию на путь `DATABASE_PATH` с владельцем `logistics:logistics` и правами `0600`. Удалите восстановленные сессии командой `DELETE FROM sessions;` через SQLite от пользователя `logistics`. Запустите сервис и проверьте вход и содержимое реестра. После восстановления пользователям нужно заново открыть приложение.

[Документация SQLite по онлайн-копированию](https://www.sqlite.org/backup.html)


## Персональные виды реестра (кандидат, схема 3)

Авторизованный GET `/api/saved-views` возвращает `{revision, views}`; PUT принимает ровно эти поля, требует CSRF/Origin и проверяет активную сессию внутри транзакции. Владелец определяется сервером, ревизия независима от заявок. Конфликт возвращает 409 без записи. Лимиты — 25 видов, имя 45 символов, тело 16 КиБ; произвольные поля/значения запрещены. Поиск и данные заявок не сохраняются в видах.

Старые виды из браузера переносятся только явной кнопкой с подтверждением. Совпадающие названия на сервере не заменяются, локальная копия сохраняется. Демо остаётся локальным. Успех показывается только после ответа сервера; после ошибки сети требуется обновить список и проверить фактическое состояние, прежде чем повторять.

Миграция 2→3 добавляет только saved_views и сохраняет пользователей, заявки, сессии и ревизии. Проверяется на временных SQLite, включая восстановление резервной копии. **Production этим этапом не мигрируется.** Старый сервер со SCHEMA_VERSION=2 откажется открывать схему 3: простой checkout старой версии не является допустимым откатом. Перед отдельным выпуском нужны проверенная предмиграционная копия, репетиция и согласованный план отката с учётом новых записей; восстановление старого снимка может потерять изменения после выпуска. Автоматического понижения схемы нет.

Целевой браузерный прогон: `python -m backend.browser_smoke --saved-views`; полный обязательный прогон без аргументов включает эти же сценарии.


## Google Sheets: проверенный режим платежей (кандидат)

Рабочий лист фактически проверен только чтением 19.11.2026: «Платежи», gid 977001198. Согласованное сопоставление: A — номер, B — всё «Наименование», C — сумма, E — имя из серверного аккаунта, I — дата обращения, L — обещанная дата. D/F/G/H/M пользовательскими значениями не заполняются. J/K — расчётные формулы; заранее заполненный J не считается концом платежей. Поля наименования не переименовываются и не интерпретируются как перевозчик автоматически.

Режим `payments_v1` в закрытой конфигурации выбирает `PaymentsSheetWriter`. В отличие от прежнего учебного `generic_af`, он проверяет идентификатор листа, полные заголовки A:M, шаблоны J/K и допустимые границы, вставляет новую строку после последней заявки одним batchUpdate и независимо копирует формат и data validation. A/B/E — stringValue, C — numberValue, I/L — serial dates с DATE; формулы J/K задаёт сервер. Оплата и значения соседней заявки не копируются. Служебная S1 сохраняется. Неподдерживаемые объединения, защита и затрагиваемые боковые данные блокируют запись.

Учебная проверка точного `build_payments_batch` через настоящий Google API успешна: значение `=1+1` осталось текстом, 12.5 — числом, даты отобразились 19/20.11.2026, J/K вычислились без ошибки, dropdown/checkbox validation и предыдущая строка сохранены, S1 не изменена. Первоначальная проверка выполнялась через connector; 19.11 дополнительно проверена настоящая серверная OAuth-цепочка, описанная ниже. Рабочая таблица не изменялась.

### Воспроизводимая учебная OAuth-проверка

`backend.live_sheets_smoke` запускается только явно с `--allow-test-writes`, путём к закрытому ключу вне checkout и коротким `--run-id`. Назначение жёстко ограничено согласованной учебной таблицей и вкладкой `Workspace API 20261119` (60261119); аргумента рабочего spreadsheet нет. Требуются зависимости requirements-sheets и requirements-test. Пример:

```powershell
.\.venv\Scripts\python.exe -m backend.live_sheets_smoke --key-file "$env:USERPROFILE\LogisticsWorkspaceSecrets\google-sheets-test\service-account.json" --run-id 20261119A --allow-test-writes
```

Скрипт использует временную синтетическую SQLite вне проекта и HTTPS TestClient защищённых маршрутов приложения. Создаёт по одной строке для двух вымышленных аккаунтов, проверяет серверное имя, отказ без CSRF и при подмене actor, повторы через маршрут, пересоздание writer и поиск дубля с чистыми квитанциями. Повтор с тем же run-id/датой не создаёт новых строк. Проверяет реальное чтение формул, вычисленных значений, типов, дат, dropdown/checkbox validation и S1. Учебные строки сохраняются как доказательство; автоматического удаления нет. Запуск с новой датой/идентификатором добавит две новые строки и требует осознанного выбора.

19.11.2026 run-id `20261119A` успешен дважды: строки 4/5, два аккаунта, шесть проверок дублей. Использован отдельный service account без IAM-ролей проекта; включён только Sheets API, право редактора выдано владельцем только учебному файлу. Ключ хранится вне Git под защищённым Windows ACL; из Downloads перемещён. Ключ и production-конфигурация на VPS не устанавливались. Истечение реального токена и физический интерфейс стенда этим скриптом не проверяются; обновление/гонки OAuth и сетевые отказы проверяются изолированными тестами.

### Авторизация и включение только после отдельного согласования

1. Установить необязательные зависимости `python -m pip install -r backend/requirements-sheets.txt` в согласованный серверный venv. Они не нужны при выключенной интеграции.
2. Подготовить отдельную Google service account с включённым Sheets API. Не выдавать роли владельца проекта или domain-wide delegation; доступ редактора выдаётся непосредственно только к учебному файлу, затем отдельно к согласованному рабочему файлу. Ключ JSON не присылать в чат, не хранить в Git; разместить вне checkout, например `/etc/logistics-workspace/google-service-account.json`, доступ только пользователю службы.
3. Создать закрытую конфигурацию по `deploy/sheets-payments.example.json`. Указать реальные email приложения → Герман/Марина, подтверждённые spreadsheet/tab/sheet_id учебного назначения и путь `service_account_file`. `token_file` остаётся альтернативой, но требует внешнего обновителя; одновременно оба источника запрещены. Официальный google-auth обновляет короткоживущий токен service account автоматически, только со scope spreadsheets; обновления сериализованы и ограничены таймаутом.
4. Согласовать `coordinated_writes: true`: на время запросов не должно быть ручных вставок/удалений/сортировки строк. Google не предоставляет этому batch атомарную ревизию относительно внешнего редактора. Собственная блокировка Workspace не защищает от всех внешних структурных правок, и readback не обнаружит каждую такую гонку. Без этого условия данный режим **не включать**; для одновременной структурной работы нужен иной согласованный механизм.
5. На отдельном стенде настроить `WORKSPACE_SHEETS_ENABLED=true`, `WORKSPACE_SHEETS_CONFIG` и собрать UI с `VITE_SHEET_PREVIEW=true`. Пройти реальные запросы двух тестовых аккаунтов, перезапуск, обновление токена, двойную отправку и ошибку связи. Только после этого отдельно согласовать рабочий файл и production-выпуск.

### Неопределённый результат и откат

После отправки batch ошибка сети/неподтверждённый readback оставляют квитанцию pending и постоянную блокировку назначения в SQLite. Автоматического таймаута блокировки и повторного batch нет: Google мог уже применить запись. Оператор сначала сверяет в листе шесть полей и формулы по исходному запросу (не публикуя данные); проверяет, не выполняется ли ещё сетевой запрос, и только затем по отдельному разрешению корректирует квитанцию/снимает блокировку. Если результат нельзя установить однозначно, оставить блокировку и не отправлять повторно. Ошибки до отправки не создают pending-квитанцию.

Быстрое отключение интеграции: убрать WORKSPACE_SHEETS_ENABLED и после согласования перезапустить службу; отозвать доступ service account при необходимости. Это не удаляет строки Google, заявки, квитанции или локальные резервные копии. Автоматического удаления тестовых/рабочих строк нет. Для кода схемы 3 дополнительно действует отдельное ограничение отката базы, описанное выше.


### Проверенный совместимый откат схемы 3

[План выпуска и отката](../deploy/SCHEMA3_RELEASE_PLAN.md) описывает сохранение **актуальных** данных вместо восстановления устаревшего снимка. На остановленной изолированной копии deploy.schema_compatibility меняет только маркер3→2 и сохраняет saved_views. Закреплённый предыдущий API2 проверен с существующими сессиями обоих аккаунтов и новыми записями; повторное обновление3 сохраняет виды и заявки. Миграция3 проверяет структуру и повторно использует только совместимую retained-таблицу. Production-команды требуют отдельного разрешения, здесь не выполнялись.
